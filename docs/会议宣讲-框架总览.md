## 〇、一页速览（投屏用）

**一句话**：用 pytest 调度、Playwright 的 Android API 驱动、跑在**真机微信里的小程序**上的 UI 自动化框架。
不用 Appium，也不用微信开发者工具。

**它解决什么**：小程序回归以前靠人手工点，点一轮半天，还会漏、会"点过了就当成通过了"。
现在这些步骤由机器重复执行，**每一步都留截图和判定结果**，红在哪一步、当时屏幕什么样，一眼能看。

### 两条使用入口

| 入口 | 谁用 | 怎么做 |
|---|---|---|
| **填表**（不写代码） | 大部分回归用例 | 在 `cases/用例表.xlsx` 里一行一步地填，然后 `python run.py` |
| 写 `.js` 用例 | 流程复杂、要读页面数据、要跟数据库对账 | `test_case/suprecast_app/` 下新建 `test_*.js` |

表填好之后由 `tools/export_cases.py` 导出成 `cases/用例表.json`，再由表格用例的执行端一条条跑。
**同一条用例 = 报告里的一个用例项**，所以表里写错了只红那一条，不会连累别的。

### 四层结构（谁改动，改哪一层）

| 层 | 位置 | 职责 | 改动频率 |
|---|---|---|---|
| 用例层 | `test_case/suprecast_app/` | 描述「测什么」：把页面操作按顺序排好 | 最常改 |
| **页面对象层** | `app_sub_function/suprecast_app/pages/` | 描述「这个页面长什么样」：选择器、页面标记、幂等导航 | **小程序改版时只改这里** |
| 关键字层 | `app_sub_function/suprecast_app/android.js` | 提供「怎么操作」：点击、输入、滑动、找前台页、断言 | 常改 |
| 驱动层 | `common/app_common.js` | 「连接与执行」：连设备、抓 WebView、跑步骤、截图 | 少改 |

一句话记住这套设计的价值：**选择器只写一遍**。用例层里不出现任何选择器，小程序改版时改动的面被压到最小。

### 一条用例跑起来发生了什么

```text
python run.py
  ① 导出表格 → ② 检查表格有没有填错 → ③ 看手机连没连、小程序在不在前台（预检）
        ↓
pytest 收集 .js 用例（conftest.py 把每个 .js 变成一个 pytest 用例项）
        ↓
启动 node 子进程跑用例；用例把步骤组装成 funcList
        ↓
连真机 → 抓小程序 WebView 的 Page → 逐步执行
        每一步：重新判定"前台页" → 操作 → 截图 → 计时
        ↓
退出码 0 = 通过；非 0 = 失败（pytest 只认退出码，这是"假绿"的第一道防线）
        ↓
控制台步骤明细 + report/photo_app 截图 + Allure 网页报告 + report/结果摘要.md
```

### 三条最值钱的经验（讲到"为什么代码长这样"时就讲这三条）

1. **小程序的视图层不认「合成事件」**：代码里模拟出来的点击，小程序不响应 —— 必须换算成手机屏幕坐标、
   让系统真实点一下（`adb` 层）。所以框架里"点击没反应"这类怪现象少了一大半。
2. **同一时刻有多个页面并存**（首页、我的、弹窗、预加载页），手里的页面随时可能降级成后台页。
   框架每一步都重新判定"谁是前台页"；另外**「定位到了」不等于「已经到达」**，这两件事在真机上被混用会造成假成功。
3. **没有断言的用例跑一百遍都是绿的**（这种叫假绿，比红更危险）。所以一条用例至少一条「检查…」，
   而且每个断言交付前都要**故意让它红一次**再改回来 —— 确认它真的会失败。

### 红线（今天讲清楚，免得以后出事）

- 测试环境没有独立测试账号，用的是 **owner 的真实账号** → **会写数据的操作默认全部禁止**，
  要跑必须显式开开关，而且**跑完必须复位**；没有复位手段的写操作（积分兑换、签到）现在不做。
- **生产环境不碰**：生产的 appid 留空，跑生产会被当场拦下（这是故意的，不是没做完）。
- **同一台手机同一时间只能一个人跑**：你、同事、别的 AI 都不行；跑的时候别上去手动点。

### 下一步（owner 已拍板的优先级：数据准备与写链路 → 易用性 → 零散需求）

眼下建议推进的三件：① 把散在用例里的固定值（关键词、活动名、课程名）抽到配置；
② 补 Python 侧的配置与日志（现在是 JS 侧管一套、Python 侧管一套）；
③ 把公共前置步骤抽出来，用例只写业务差异。

## 一、讲稿（20 分钟，照着讲）

### 0:00–2:00 开场：为什么要做它

> "我们小程序的回归测试，以前是靠人手工点。一轮下来半天，而且有两个老问题：
> 一是**会漏**，二是**点过了就当通过了** —— 到底验没验，说不清。
> 这套框架就是把手工点变成机器点，而且每一步都留证据。
> 一句话：**用 pytest 调度、Playwright 驱动、连真机上微信里的小程序，不用 Appium、也不用开发者工具。**"

要强调的一点：它不是"又一个自动化框架"，是**给这个业务量身做的**：真机、真实账号、真实运营数据。

### 2:00–6:00 它长什么样：四层 + 一个关键设计

投屏第〇节的四层表格，然后讲这一句：

> "最重要的一条设计：**选择器只出现在页面对象层**。
> 用例里写的是'打开搜索页 → 输入关键词 → 检查文字'，
> 不写 `#id`、不写 class。小程序改版的时候，我们只改页面对象一处，
> 几十条用例一行都不用动。"

顺手把"两条入口"讲掉：**不写代码的人填 Excel，一行一步；复杂流程才写 `.js`。**

### 6:00–11:00 一条用例怎么跑起来 + 两条真机经验

投屏链路图，按 ①→⑥ 走一遍（不用念细节，讲"每步都截图、退出码决定成败"）。
然后讲这两条，**这是全场最能体现工作质量的地方**：

> 经验一：小程序不认代码模拟的点击，必须让手机系统真实地点一下 ——
> 我们为此把点击换算成屏幕物理坐标走 `adb`，这是真机实测踩出来的，不是设计书上抄的。
>
> 经验二：页面里同时存在好几个"页"，手里的那个随时会变成后台页。
> 结果就是"页面明明已经切过去了，判定却说没切"，然后反复点、点到超时。
> 现在框架每一步都重新判定前台页；另外我们把「定位到了」和「已经到达」严格分开 ——
> 这两件事混用，会造出**0.55 秒的假到达**。

### 11:00–15:00 零基础的人怎么自己加用例

> "回归用例大部分由测试同学自己加，不用写代码：打开 `cases/用例表.xlsx`，
> 一行一个步骤，动作从下拉框里选（60 个动作分 6 类，见 `docs/动作清单-分类.md`）。
> 表格最后还有一列可选的「类型分类」（也是下拉框）：操作型 / 展示文案型 / 业务规则与数据型 ——
> 表里按类型上了底色（蓝/绿/橙/灰），一眼看得出哪条是哪类；
> 它是给**挑着跑**用的：改版或换设备后先跑「操作型」那批当冒烟，发版回归再跑业务规则那批。
> 唯一的硬要求是：**每条用例至少有一条「检查…」**，
> 而且改完要**先故意让它红一次** —— 把期望值改错、跑一次、确认真的失败，再改回来。
> 不做这一步，你永远不知道那条断言是不是写了个永远成立的条件。"

### 15:00–20:00 质量怎么保证 + 现状 + 请大家配合什么

> "这套框架最怕的不是报错，是**看起来通过了、其实没测到**。所以凡是'坏了也不报错'的地方，
> 都配了一条自动检查：一条命令 `python scripts/verify-all.py`，不需要手机，几秒钟跑完 ——
> 语法、用例能不能被收集、文档里的路径和索引有没有漂、表格规则、数据安全、框架完整性，全在里面。
> 另外每次跑完有中文摘要 `report/结果摘要.md` 和带截图的网页报告，红了先看失败那一步的截图。"

现状与边界（照实说）：

- 已覆盖：**11 条需求**（完整或部分覆盖，清单在 `knowledge/可自动化需求清单.md`）+
  **8 条历史缺陷的回归用例**（盯住 9 个缺陷，表格 5 条 + `.js` 3 条，清单在 `knowledge/缺陷回归清单.md`）；
- 测不了的：走系统 UI 的（分享到朋友圈）、需要造数据才成立的（每日积分上限），都明确写在清单里，不假装覆盖；
- 偶发失败**不自动重跑**（UI 重试会重复点击，可能把偶发失败变成状态污染），红了先单条复跑确认。

请大家配合的两件事：

1. **新需求上线后告诉我们**（或者在清单里挑编号），我们按"只读优先"的顺序接着写用例；
2. **别在跑用例的时候动那台手机**，也**别刷新/重开小程序** —— 现场会被破坏，报错会很怪。

## 二、现场演示（约 3 分钟，可选但效果最好）

开跑前 30 秒自检：手机连着、`adb devices` 能看到设备、微信里的小程序开着、这台手机没有别人在用。

```powershell
python run.py -k ZW_002        # ① 跑一条绿的：看控制台的步骤明细和截图路径
python scripts/verify-all.py   # ② 一条命令跑完全部离线检查：看"闸门"是干什么的
```

想演示"假绿"这个概念（很有说服力，但要留时间改回来）：

1. 在 `cases/用例表.xlsx` 里把 `ZW_002` 某条「检查文字显示」的期望值改错一个字；
2. `python run.py -k ZW_002` → **它会红**，并且告诉你红在哪一步、当时屏幕什么样；
3. 把值改回来，再跑一次变绿。

> 这一步的意义：证明**断言是真的会失败的**。讲完这句，听众对"通过"这两个字的信任度会完全不一样。

## 三、可能被问到的问题（照着答）

**Q1 为什么不用 Appium？**
现状是直接连真机上的微信、抓小程序 WebView 的 `Page` 对象，用标准 Playwright 的 DOM 定位操作元素，
省掉了 Appium server 那一层。代价是强依赖 playwright 与 `adb`，环境要求更集中（Node + Python + 一台真机）。

**Q2 一定要真机吗？模拟器行不行？**
目前所有验证都在真机上做的（框架用 `adb` 连设备；接了多台会直接报错，不会随便挑一台静默跑错对象）。
模拟器、云真机都没实测过 —— **没实测过的东西我们不会写进文档说能用**，这是这个仓的规矩。

**Q3 为什么一半 Python 一半 Node？**
pytest 负责调度、收集、报告：`conftest.py` 把每个 `.js` 用例包成一个 pytest 用例项，**用例成败由子进程退出码决定**；
用例本身用 Node 写，因为驱动用的是 Node 版 Playwright 的 Android API。
表格导出、数据库工具、离线闸门这些则用 Python。

**Q4 小程序改版了怎么办？**
改页面对象里的选择器，改动只在一层；改完跑一次离线检查、再跑相关用例。
另外我们有 `tools/scan_anchors.py`，可以拿小程序前端源码查"这个 class 是不是真的存在、是不是业务类名"
—— 抄了编译出来的原子类（`fs-28` 这种）会今天绿、明天红，已经在踩坑记录里单独记了一条。

**Q5 用例稳定吗？偶发红怎么处理？**
55 条实战坑都记在案，大多是"看着像功能坏了、其实是测量方式错了"（点不到、认错页、判据盯着会变的文案）。
现在的规矩：**不自动重跑**，红了先 `-k` 单条复跑分清偶发还是真问题，再打开失败那一步的截图看现场。

**Q6 会不会动到真实数据 / 跑到生产上？**
两道硬闸：写操作默认全禁，必须显式开开关才能跑，而且写链路用例**跑完必须复位**（复位工具默认只预览，`--yes` 才真删）；
生产 appid 留空，`--env prod` 会被当场拦下。`scripts/check-safety.py` 会盯着表格里别混进写操作词。

**Q7 覆盖了多少？**
11 条需求（含部分覆盖）+ 8 条历史缺陷的回归用例；表格 30 条用例 171 步，`.js` 用例 11 条。
知识库里 247 条需求、545 条缺陷都筛过一遍，能自动化的候选清单在 `knowledge/可自动化需求清单.md`，
不适合自动化的原因也写在里面（免得反复讨论）。

**Q8 不写代码的人真能加用例吗？**
能：填表 + 一条「检查…」+ 反向验证一次。手册是 `docs/使用手册-零基础.md`（不含代码）。
只有三种情况需要找我们：小程序改版、要加新动作、要做会写数据的用例。

**Q9 跑一轮多久？**
单条通常 20 秒到 1 分钟（取决于流程长短），全量一轮十几分钟。所以适合回归，不适合每次提交都跑。

**Q10 能挂定时 / CI 吗？**
现在没有。硬约束是必须有一台真机常驻、且同一时间只能一个人用；
另外没有独立测试账号，定时跑写操作风险太大（owner 已拍板：暂时不挂）。

**Q11 和同事那两个仓什么关系？**
`webzdh4.7/` 是同事的 Web UI 框架，我们借了它的工程化做法（步骤日志、用例上下文、统一入口）；
`miniapp-flow/` 是团队的工作流仓（规范与复盘），本仓的离线闸门、文档防腐、并发纪律、数据安全口径都来自它。

**Q12 下一步要什么支持？**
① 新需求上线后给个信号，或者直接说"按你推荐的挑"；
② 想扩大覆盖面（尤其是写链路、每天自动跑），前提是一个独立测试账号 —— 现在用的是 owner 的真实账号；
③ 想让它进流程（比如发版前必跑），需要一个固定的跑测时段 + 一台专机。
