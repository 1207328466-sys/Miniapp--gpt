## 二、小程序并存页面的真实结构（已确认）

`context.pages()` 里同时存在 **7 个 page**，来自 **2 个不同小程序**（实测数据）：

| # | appid | 身份 | 元素数 | RAF 活跃 | 可见文本 |
|---|---|---|---|---|---|
| 0 | wx3de2e1d179b60303 | `/preload/` 预加载页 | 9 | ❌ | 空 |
| 1 | wx3de2e1d179b60303 | 压铸百科页 | 362 | ❌ | 课程 专栏 压铸百科... |
| 2 | **wx6bd2fb149a93a9c5** | **另一个小程序** | 17 | ❌ | 空 |
| 3 | wx3de2e1d179b60303 | **首页**（社区百科） | 418 | ✅ | 压铸人的社区百科... |
| 4 | **wx6bd2fb149a93a9c5** | **另一个小程序** | 14 | ❌ | 空 |
| 5 | wx3de2e1d179b60303 | 用户中心 | 186 | ❌ | 西城 / 2.6万 积分... |
| 6 | wx3de2e1d179b60303 | 未知 | 11 | ❌ | 空 |

**关键结论**：

1. **同一小程序同时缓存多个页面**（首页 / 压铸百科 / 用户中心 / 预加载 / 空壳）
2. **不同小程序的 page 混在同一个 context 里**——选页必须校验 appid
3. **只有屏幕上正在显示的那个 page 的 `requestAnimationFrame` 活跃**，其余全部 `false`
4. 因此 **RAF 是可靠的"前台页"判据**（实测：7 个里只有 1 个为 true，且与截图一致）

### 被推翻的旧结论

| 旧结论 | 实际情况 | 推翻依据 |
|---|---|---|
| "底部 tab 栏是原生组件，不在 WebView DOM 里" | **在 DOM 里**（`wx-view.tab-item` > `wx-text.text` > `span`） | 完整 DOM 写入文件后 grep 到 |
| "点「我的」没反应，可能 tab 点不动" | **能点动**，只是点击后需要等待页面切换 | 加 3 秒等待后成功选中 |
| "`getForegroundPage` 可能不可靠" | **可靠**，RAF 判据实测唯一命中 | 7 个 page 的 RAF 对比 |

### RAF 判据的可靠性（2026/10/10 二次校准）

用 **adb 截图当"真值"**复核过 RAF 判据：截图确认屏幕上显示的是用户中心（底部「我的」tab 高亮），
同一时刻只有 186 元素那个 page 的 RAF 为 `true`，连续 3 轮采样结论一致 —— 判据成立。

同时**排除**掉两个看起来很合理的候选判据（实测在**所有** page 上都无法区分前后台）：

| 候选判据 | 实测结果 | 结论 |
|---|---|---|
| `document.visibilityState` | 所有 page 都返回 `visible` | ❌ 不可用 |
| `document.hasFocus()` | 所有 page 都返回 `true` | ❌ 不可用 |

**但 RAF 不是绝对判据。**页面切换的过渡窗口里，新旧两个 page 可能**短暂同时**出帧：
实测从专栏列表页进详情页时，旧列表页（188 元素）与新详情页（118 元素）同时为 `true`。
所以 `resolveForegroundPage` 里加了"多候选二次探测"来消歧 —— 详见根因 10。

还有一个易踩的观察：`context.pages()` 里各页面的**元素数会漂移**，同一类页面在不同时刻
可能报 217/188、403/374、186/157 等不同值。**不要把元素数当成页面身份**，它只能当量级参考。

## 三、滚动结构（已确认）

首页有 **11 个 CSS 层面可滚动的容器**，但只有 1 个是真正的页面主滚动区：

| 分类 | 容器 | 说明 |
|---|---|---|
| **主滚动屏** | `div.wx-scroll-view`（347x593，内容 1606） | 真正的垂直滚动容器 |
| 轮播（横向） | `wx-swiper-wrapper` / `wx-swiper-slides` / `wx-swiper-slide-frame` | 2 组，只能横向滚 |
| 假阳性 | `wx-view.img-box` / `nut-image` | 内容 285 / 可视 217，实际不滚动 |

### 合成事件 vs 真实事件（实测对比）

| 操作 | `page.mouse` 合成 | `adb input swipe` |
|---|---|---|
| **垂直滚动** | ❌ 11 个容器 `scrollTop` 全部纹丝不动 | ✅ `wx-scroll-view` 滚动 **468px** |
| **点击 tab** | ❌ `.click()` 超时（元素不可点） | ✅ 能选中「我的」 |

**结论（取代之前的绝对化表述）**：

> 对小程序视图层的**交互操作**（点击、滑动），必须使用真实触摸事件（adb）；
> 合成事件对滚动和大多数点击无效。
> 但**只读操作**（读取 DOM、`scrollTop`、`boundingBox`、`evaluate`）不受影响。

## 五、已定位并修复的根因

### 根因 1：`appTest` 可能返回预加载空壳页（已修）

**文件**：`common/app_common.js`

**原始逻辑**：

```js
if (url.includes("servicewechat.com")) {
  page = pageTmp;   // 7 个 page 的 URL 都含这个特征
  break;            // 撞上第一个就返回
}
```

实测它撞上的是 `https://servicewechat.com/preload/page-frame.html`——**预加载空壳页**，只有 `<body><div>`，导致后续所有元素定位全部超时。

**修复**：新增 `pickForegroundPage()`，用 RAF 判据选真正的前台页，并校验 appid 避免跨小程序选错。

**修复后实测**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 元素数 | ~2 | 418 |
| 是否前台页 | false | true |
| 可见文本长度 | 0 | 186 |
| 带 id 的元素数 | 0 | 231 |

### 根因 2：`#id` 选择器语法对小程序 id 失效（已修）

小程序自动生成的 id 形如 `3e41d18d--_yr`——**以数字开头、含连续双横线**，在 CSS 选择器里非法：

```
[FAIL] #3e41d18d--_yr              → SyntaxError: not a valid selector
[OK]   [id="3e41d18d--_yr"]        → 匹配到 1 个元素
```

**影响范围**：`clickElementById`、`inputText`、`assertElementExists` 三个函数对小程序元素**全部失效**。

**修复**：`page.locator(\`#${elementId}\`)` → `page.locator(\`[id="${elementId}"]\`)`（3 处）。

### 根因 3：`getByText` 缺 `.first()` 触发 strict mode 冲突（已修）

首页同时存在「我的」和「我的关注」两个文本，`getByText("我的")` 在 strict mode 下抛：

```
strict mode violation: getByText('我的') resolved to 2 elements
    1) <span>我的</span>
    2) <span>我的关注</span>
```

**修复**：`switchToUserCenter` 里的 `getByText("我的")` 补上 `.first()`。

**注意**：这个 bug 的表现**取决于当前页面内容**——在「课程」页只有 1 个「我的」，不会报错；在首页就会报。属于典型的"时好时坏"。

### 根因 4：`switchToUserCenter` 在过时的 page 对象上做验证（已修）

**现象**：该函数连续多轮报 `page.waitForFunction: Timeout 10000ms exceeded`，但**截图显示页面其实切换成功了**。

**定位过程**（逐步截图诊断）：

```
tap 前：[基线 page] 元素数=403  在首页=true
tap 后：[tap 后 page] 元素数=403  在首页=true     ← 旧 page 内容没变！
        tap 后 appTest 的 page 是否仍是前台页: false
        !! page 已变成后台页，前台页是另一个对象
        [tap 后前台页] 元素数=186  在用户中心=true   ← 实际切换成功了
```

**根因**：小程序切 tab 时**有时会创建新的 page 对象**，旧的变成后台页，其 `innerText` **冻结在切换前的内容**。在旧 page 上等「积分商城」**永远等不到**，于是必然超时。而且它 `return page` 返回的还是失效对象，会坑害调用方。

> 重要细节：这个行为**不是每次都发生**——另一次诊断中 tap 后原 page 就直接是新的用户中心页。所以框架**必须两种情况都能处理**，不能假设"page 会复用"。

**修复**：

```js
// 点击后必须重新获取前台页再验证，并返回前台页
const deadline = Date.now() + timeout;
while (Date.now() < deadline) {
  if (await checkOnForeground()) {          // 内部用 pickForegroundPage
    const fg = await pickForegroundPage(page);
    return fg;                              // 返回前台页，不能返回旧 page
  }
  await page.waitForTimeout(400);
}
```

同时新增**幂等**（已在用户中心直接返回）与**重试**（连续切换偶发失败时重试一次）。

**验证结果（4/4 通过）**：

| 测试 | 结果 |
|---|---|
| 从首页切换到用户中心 | ✅ 5915ms |
| 幂等（已在用户中心再调） | ✅ 正确识别并直接返回，3283ms |
| 连续切换（复现失败场景） | ✅ 5726ms |
| `swipeUp` 滚动校验 | ✅ 检测到位移，877ms |

### 根因 5：`swipeUp` 用合成鼠标事件（已修）

**实测对照**（判据：元素位置变化）：

```
page.mouse 合成滑动 → 页面无位移，完全无效
adb input swipe     → 页面位移成功
```

**修复**：改用 `device.shell("input swipe x1 y1 x2 y2 duration")`，并新增"是否真的位移"校验——不位移就抛错，避免"发了 swipe 就当成功"的假通过。

### 根因 6：所有点击都用合成 `.click()`（已修）

**实测对照**：

| 场景 | 合成 `.click()` | 真实 `tapElement` |
|---|---|---|
| 底部 tab 栏「我的」 | ❌ Timeout 8000ms，页面无变化 | ✅ 成功切换 |
| 顶部筛选栏「推荐」 | ⚠️ 同样 Timeout，但内容其实变了（**误报失败**） | — |

**根因**：Playwright 的 `.click()` 会等元素 "visible, enabled and stable"，其中 **stable 要求元素连续两帧位置不变**。小程序页面持续重绘，元素永远不稳定，于是 `.click()` **要么超时抛错、要么误报失败**——无法区分成功与失败。

**修复范围**（8 处）：`clickElementByText`、`clickWxText`、`clickElementById`、`switchToUserCenter`、`login`（4 处）、`inputText`（聚焦）。

**额外改进**：`inputText` 新增"fill 后读回校验"，因为小程序自定义输入组件可能不接受浏览器层面赋值，`fill()` 不报错但内容为空 —— 典型的假通过。

### 根因 7：`tapElement` 按零宽文字节点取坐标（已修）

**现象**：同一目标有时点得中、有时点不中。

**实测数据**：

```
[4] "我的"  tab-item 容器 x=277.7 y=673.3 w=69.4 h=61.0   ← 几何正常
            文字 span   x=323.4 y=686.0 w=0.0  h=22.0   ← 宽度为 0
```

**修复**：新增 `findClickableAncestor()`，从元素向上找"尺寸正常且增长不过分"的祖先容器，用它的中心点击。三条约束防止爬过头点到页面正中间：面积 > 400、面积 ≤ 起点 8 倍 + 2000、最多向上 4 层。

**验证**：`tapElement` 点击「我的」成功切换页面。

### 根因 8：小程序导航会销毁 page 对象，旧引用直接失效（用例侧已绕过，框架侧待修）

**发现场景**：编写用例 `test_learn_center_column.js`（学习中心 -> 专栏 -> 第一张专栏）时，
从专栏详情页点顶部返回按钮回到列表页。

**现象**：

```
已点击顶部返回按钮（匹配 1 个）
[ERROR] page.waitForTimeout: Target page, context or browser has been closed
[ERROR] 异常：原 page 已关闭，且无法从它的 context 获取其它页面
```

点击成功，但**原 page 对象被销毁**，后续所有操作报 "has been closed"。

**定位过程**：用 `dump_page.js` 查看 context 状态，发现小程序**已经回到列表页**
（217 元素），说明导航是成功的，只是 page 对象换了。

**这比"page 变后台页"更严重**：

| 情况 | page 对象状态 | 内容 | 能否继续用 |
|---|---|---|---|
| 后台页 | 有效 | 冻结在切换前 | 能读，但内容过时 |
| **被销毁** | **无效** | — | **完全不能碰** |

**两层坑**（第二层更隐蔽）：

1. 导航后旧 page 报 "has been closed"，必须重新取页面。
2. **`page.context()` 对已关闭的 page 会失败** —— 想从旧 page 拿 context 去找兄弟页面也不行。
   必须在**导航发生之前**就把 `context` 引用保存下来（`context.pages()` 在页面切换后依然有效）。

**第三个坑（本次最耗时）**：导航后旧 page 可能**仍然返回 `isClosed() === false`，
但已不在 `context.pages()` 里** —— 这是一个"孤儿引用"，内容冻结在切换前。
只检查 `isClosed()` 会漏过它，导致后续所有判据都作用在错误的页面上。

正确的"引用是否还活着"判断：

```js
const isLive = () => {
  if (!page || page.isClosed()) return false;
  if (!appContext) return true;                    // context 还没记录，暂时信任
  return appContext.pages().includes(page);        // 关键：必须在册
};
```

**框架侧已修（2026/10/10，第二轮改造）**：

新增 `resolveForegroundPage(page)` 作为**唯一的**"取当前前台页"入口，一次兜住三种失效形态：

| page 状态 | 表现 | 是否被兜住 |
|---|---|---|
| 正常前台页 | — | ✅ 直接返回 |
| **已降级为后台页** | 活着、在 `context.pages()` 里，但内容冻结 | ✅ 重新探测选出真前台页 |
| **已被销毁** | `isClosed() === true` | ✅ 从缓存的 context 重新获取兄弟页面 |

关键实现点：

- **context 缓存**：`page.context()` 对已销毁的 page 会抛错，所以第一次拿到时就存下来
- **并行 RAF 探测**：串行探测 7 个页面最坏要等 3.5 秒，放到每步之前会严重拖慢用例
- **appid 过滤**：context 里会混入别的小程序的 page；取不到 appid 时按出现频次推断
- **多候选二次探测**：过渡窗口里新老页面会同时出帧，见根因 10

同时 `runAppSteps` 在**每个步骤开始前**自动重新解析前台页，用例侧不再需要自己写
"重新获取页面"那套代码（`test_learn_center_column.js` 里约 100 行的自愈逻辑已删除）。

**验证**：用例 `test_learn_center_column.js` 从三种不同起点各跑一次全部 PASSED
（详细记录见第十二节）。

### 根因 9：同一个函数里用两个不同来源的判据，结论会自相矛盾（用例侧已修）

**现象**：用例第 4 步（验证已进入详情页）反复失败，日志自相矛盾：

```
当前页面前 200 字: "互动专栏 已订阅 ... N1-预热期专栏 ..."   <- 内容是详情页
详情页标记「.col-title」存在: false                        <- 但选择器查到 0
```

**根因**：同一个函数里用了**两个不同页面的判据**：

| 判据 | 作用在哪个页面 | 结果 |
|---|---|---|
| `visibleText(page)` | 内部调 `pickForegroundPage` → **前台页（详情页）** | 看到详情内容 |
| `isOnDetail(page)` | 传入的 `page` → **可能是后台的列表页** | `.col-title` = 0 |

**修法**：所有判据必须作用在**同一个页面**上。统一以 `pickForegroundPage` 的结果为准，
并用它同步更新 `page` 变量。

**验证证据**（`probe_detail_selector` 的输出）：

```
page[0]  RAF=true   元素118  .col-title -> 1   "互动专栏..."     <- 详情页（前台）
page[2]  RAF=false  元素188  .col-title -> 0   "热门专栏..."     <- 列表页（后台）
```

同一时刻两个页面并存，判据不统一必然得出矛盾的结论。

**教训**：**"页面"这个概念在框架里必须是唯一的、显式的**。
一旦函数内出现"我用的 page"和"前台 page"两个概念，就会埋下这类 bug。

### 根因 10：过渡窗口里新旧页面同时出帧，按"元素最多"挑会选错（已修）

**现象**：`resolveForegroundPage` 第一版在多候选里按"元素最多"挑，结果**选中了过期的页面**：

```
[DEBUG] 前台页解析: 候选=4 活跃=2 元素数=188      <- 挑中了 188 元素的旧列表页
  已点击第一张专栏卡片
[DEBUG] 前台页解析: 候选=5 活跃=1 元素数=118      <- 真实前台是 118 元素的详情页
```

**根因**：页面切换是渐进的，新旧两个 page 会**短暂同时产出动画帧**。此时"元素最多"
这个启发式规则会稳定地选中**更大但已经过期**的那一个（旧列表页 188 > 新详情页 118）。

**修法**：出现多个候选时**先等 250ms 再探一轮**，让过渡结束；只有仍然分不清时才退化为
按元素数挑，并打日志说明。

**教训**：单一启发式规则都有边界，而"过渡态"是 UI 自动化里最脏的一类时刻。
遇到歧义时**多采一次样**，比事后解释为什么选错便宜得多。

### 根因 11：选择器用子串匹配，把容器也命中且排在首位（用例侧已修）

**现象**：同一条用例、同样的坐标，点击「专栏」tab **时好时坏** ——
有时正常切到专栏列表，有时小程序直接跳回上一个底部 tab。

**取证**：把两种选择器命中的实际几何打印出来，真相立刻清楚了：

```
[class*=header-tab] -> 4 个
   {"cls":"course-header-tabs","x":11,"y":59,"w":164,"h":22}          <- 容器，排第一
   {"cls":"h5-view header-tab","x":11,"y":59,"w":30,"h":22}           <- 「课程」
   {"cls":"h5-view header-tab active","x":63,"y":59,"w":30,"h":22}    <- 「专栏」
   {"cls":"header-tab","x":115,"y":59,"w":60,"h":22}                  <- 「压铸百科」
.header-tab -> 3 个    <- 精确类名，容器不再被命中
```

容器 `course-header-tabs`（class 里同样含 `header-tab` 这段子串）被一起匹配，
且**排在第一位**，于是 `.first()` 选中的是容器：

- 容器中心 x = 11 + 164/2 = **93**
- 「专栏」tab 是 x=63 宽 30 → 右边界 = **93**

**点击坐标恰好落在 tab 的右边界上**，点中与否取决于 1 像素的边缘 —— 这就是"时好时坏"的机制。
实测点击坐标：容器中心 **(326, 245)** vs tab 自身中心 **(273, 245)**。

**修法**：改用精确类名 `.header-tab`。附带收益：`active` 判定从"读容器的 class"
（永远判为未选中）变成"读该 tab 自己的 class"，能正确识别"已选中、点击是幂等操作"。

**教训**：

1. **子串属性选择器 `[class*="..."]` 是陷阱**，很容易连容器一起命中；而 DOM 顺序上
   容器通常在外层、排在前面，`.first()` 必然踩中。
2. **命中数量本身就是信号**：日志里 `共 4 个，其中匹配 2 个` 已经在提示
   "有一个不该命中的东西被命中了"。
3. **同一个坐标在不同轮次结果不同**时，第一反应应该是"这个坐标算错了"，
   而不是"框架不稳定"。

## 十三、断言层（第三轮新增，2026/10/10）

### 为什么需要它

在此之前框架只有 `assertElementExists` 一个断言（而且只能按 `id` 判断元素是否存在）。
后果是：**功能坏了用例照样报 passed** —— 一条没有断言的用例只能证明"流程没报错"，
不能证明"界面真的对"。这是最危险的一类假通过，因为它让人误以为有覆盖。

### 四个函数

| 函数 | 断言什么 | 关键实现 |
|---|---|---|
| `assertTextVisible` | 页面**可见文本**包含某段文字 | `document.body.innerText` + 轮询 |
| `assertTextNotVisible` | 页面可见文本**不再**包含某段文字 | 同上，反向 |
| `assertSelectorExists` | 选择器命中数 ≥ 1 | `locator().count()`（不用 `visible`，小程序元素常是零宽度） |
| `assertSelectorCount` | 选择器命中数 **==** `expected` | 同上，精确比对 |

### 三条设计约定

1. **断言前先解析当前前台页**（`resolveForegroundPage`）。断言和操作一样，必须作用在
   屏幕上真正显示的那个 page 上；否则会拿冻结的后台页做判断，出现与根因 9 同类的自相矛盾。
2. **等待与断言合体**。小程序时序抖动大，"点完立刻断言"几乎必然失败；让用例自己 `sleep`
   猜时间则既慢又不稳。把等待内建进断言，用例只负责表达"期望什么"。
3. **失败信息自带现场证据**：当前前台页元素数 + 可见文本前 200 字。否则只报"没找到元素"，
   还得回去翻截图对时间。

另外它们**返回真正断言过的那一页**，所以 `runAppSteps` 会把最新 page 传给后续步骤 ——
断言顺便起到了"刷新 page"的作用。

### 验证（真机 `3B1F64EA9BBUTE00`）

**正向**：`test_learn_center_column.js` 接入这 4 个断言后全流程 PASSED
（`assertTextVisible` 0.51s、`assertSelectorExists` 0.52s、
`assertSelectorCount` 0.52s、`assertTextNotVisible` 0.51s）。

**反向（更关键）**：断言本身也要验证"该失败时真的失败"。故意传不存在的文本/选择器、
故意把期望数量写错 —— 4 个断言全部正确失败，报错形如：

```
断言失败: .col-title 命中 1 个，期望 99（等待 1000ms 超时）
  当前前台页: 元素数=118
  可见文本前 200 字: "互动专栏 已订阅 互动尚未开始，内容先睹为快..."
```

**教训**：给框架增加"判定通过/失败"的能力时，**必须同时验证正反两个方向**。
只验证正向，等于换一种方式继续生产假通过。
