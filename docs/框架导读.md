## 一、一句话定位

这是一套 **用 pytest 当调度器、用 Playwright 的 Android 实验性 API 当驱动、用 Node.js 写用例** 的微信小程序 UI 自动化框架。

它不依赖 Appium、不依赖微信开发者工具，直接连真机上的微信，抓取小程序 WebView 的 `Page` 对象，然后用标准 Playwright 的 DOM 定位能力操作小程序元素。

## 三、核心执行链路（最重要的一张图）

以执行 `test_example.js` 为例，完整链路是：

```
① 命令行：pytest（在 test_case/ 目录下）
        │
        │  pytest 启动，读取 pytest.ini
        ▼
② conftest.py 的 pytest_collect_file 钩子
   · 发现 test_*.js → 包成 JsTestFile / JsTestItem
   · 关键点：pytest 不认识 .js，是靠这个钩子"骗"它收集的
        │
        ▼
③ JsTestItem.runtest()
   · shutil.which("node") 找到 node
   · subprocess.run([node, 用例.js], capture_output=True)
   · 子进程 exit code != 0 → 抛 JsTestFailure → pytest 标记为 FAILED
        │
        ▼
④ test_example.js 里的 async IIFE 开始跑
   · 组装 funcList = [[操作函数, 参数字典], ...]
        │
        ▼
⑤ appTest(funcList, { photosPath })
   ├─ android.devices()            连设备（Playwright _android）
   ├─ getWxWebviewPage(device)     遍历 device.webViews()，挑 url 含 servicewechat.com 的那个
   │     ├─ waitForLoadState("domcontentloaded")
   │     └─ waitForFunction(clientWidth > 10)   等视口就绪
   ├─ getCaller()                  反射调用栈，拿到"哪个文件哪个函数"用于截图命名
   └─ runAppSteps(page, funcList, photosPath, caller)
        └─ for [func, kwargs] of funcList:
             ├─ 先用 resolveForegroundPage(page) 重新解析当前前台页（关键，见要点 3）
             ├─ kwargs 为空 → func(page)
             ├─ 否则       → func(page, kwargs)
             ├─ 每步截图到 report/photo_app/<文件>_<函数>/_<步骤>_<时间戳>.png
             ├─ 每步计时，最后打印耗时统计
             └─ 步骤抛错 → 先存起来(savedError) → 截图 → 再抛出
        │
        ▼
⑥ 每个业务函数内部
   · 定位：page.locator("#id") / page.getByText("文本")
   · 点击：真实 adb tap（关键设计，见下）
   · return page（链式传递，page 可能被替换成前台页）
```

## 四、五条必须理解的设计要点

### 要点 1：pytest 只做"入口"，不做驱动

`conftest.py` 把每个 `.js` 文件变成一个 pytest 测试项，用 `subprocess` 起 node 跑。
所以：

- **JS 里的 `console.log` 能被 pytest 捕获并打印**（`capture_output=True` 后手动 print），你在报告里能看到日志。
- **JS 里 `process.exit(1)` / 未捕获异常 → 该 pytest 用例 FAILED**。这就是 `test_example.js` 末尾写 `.catch(e => { console.error(e); process.exit(1); })` 的原因。
- pytest 的 marker、reruns、html 报告这些能力，对 JS 用例同样生效。

### 要点 2：小程序视图层不响应合成事件 → 必须真实 tap

> **⚠️ 2026/10/10 实测修正**：本节结论得到确认，但范围需要更准确的界定，
> 且原代码里"先尝试 `locator.click()`"的做法**已被证明不可靠并全部改掉**。
> 完整证据见 [框架能力与问题账本.md](框架能力与问题账本.md)。
>
> | 操作 | 合成事件（Playwright） | 真实事件（adb） |
> |---|---|---|
> | 点击 tab 栏等组件 | ❌ 超时，或**在点击实际成功时误报失败** | ✅ 有效 |
> | 上下滑动 | ❌ 页面零位移 | ✅ 滚动 468px |
> | 读取 DOM / scrollTop / 坐标 | ✅ 有效（不涉及交互，不受影响） | — |
>
> **为什么 `.click()` 连"误报"都会发生**：Playwright 的 `.click()` 会等元素
> "visible, enabled and **stable**"，其中 stable 要求元素连续两帧位置不变。
> 小程序页面持续重绘，元素永远不稳定 → 要么超时抛错，要么点击已成功却报超时。
> **这种"无法区分真假"的特性比单纯失败更危险。**
>
> 因此框架已把**所有交互**（8 处点击 + 滑动）统一改走 adb 真实事件。

这是整个框架最"值钱"的一条经验，写在 `android.js` 的 `tapElement` 注释里：

> 小程序视图层只响应真实触摸事件，Playwright 合成的鼠标事件点了没反应。

所以对于 `wx-view` 这类元素，流程是：

```
locator.boundingBox()   取 DOM 坐标
page.evaluate(devicePixelRatio)   取缩放比
坐标 × dpr             换算成屏幕物理坐标
device.shell("input tap x y")     走 adb 真实点击
```

**注意**：`tapElement` 现在还会**先向上寻找"可点击的祖先容器"**再取坐标。
原因是实测发现小程序里很多文字节点的盒子宽度为 0：

```
"我的"  tab-item 容器 x=277.7 w=69.4   ← 几何正常，是真正响应点击的区域
        文字 span   x=323.4 w=0.0    ← 宽度为 0，按它取中心会点偏
```

**写用例时的判断准则**：凡是需要"点一下/滑一下"的交互，一律走 `tapElement` / `swipeUp`，不要用 `locator.click()` / `page.mouse`。

### 要点 3：一个 context 里有多个 Page，必须动态找"前台页"

小程序在同一个 browser context 下并存多个视图层 page（首页 / 我的 / 弹窗页 / 预加载页）。
页面切换后，**你手里的 page 会变成后台页，再操作它会一直等到超时**。

框架的解法是 `common/app_common.js` 里的 **`resolveForegroundPage(page)`**：

| 判据 / 工具 | 思路 | 说明 |
|---|---|---|
| `resolveForegroundPage(page)` | 谁是前台？**看谁还在产生动画帧**（后台页渲染线程被挂起，`requestAnimationFrame` 不触发） | **首选，通用**；一次兜住"已销毁"和"已降级为后台页"两种失效 |
| `findPageWith(page, selector)` | 谁含有目标选择器，谁就是目标页 | 已知目标页有独特元素时（在 `android.js`） |

⚠️ 三个**实测不可用**的判据，别浪费时间：
`locator.isVisible()`（后台页元素同样返回 `true`）、
`document.visibilityState` 与 `document.hasFocus()`（在所有 page 上都返回 `visible` / `true`）。

⚠️ RAF 判据也不是万能的：页面切换的**过渡窗口**里新旧两个 page 会短暂同时出帧，
所以 `resolveForegroundPage` 在多候选时会**二次探测消歧**。

**这件事框架已经自动化了**：`runAppSteps` 在每个步骤开始前都会重新解析前台页，
用例里不用再自己写"重新取 page"。但如果你在**同一个函数内部**做多次判断，
必须**先解析一次、存成一个变量，让所有判断都用它** —— 否则"两个判据看两个页面"，
结论必然自相矛盾（账本 根因 9）。另外**业务函数仍然必须 `return page`**。

### 要点 4：输入框必须等软键盘真的弹出来

`waitImeShown(device, page)` 轮询 `adb shell dumpsys input_method`，匹配 `mInputShown=true`。

原因：输入框没真正拿到焦点时，`adb shell input text` 的事件会被系统丢弃——**不报错，但字没进去**。这是最隐蔽的一类假通过，所以框架宁可先等键盘。

### 要点 5：截图与失败处理的顺序

`runAppSteps` 的 `finally` 块保证"**即使步骤失败也要先截图，再抛异常**"，所以失败现场总能留下证据。
截图路径规则：

```
report/photo_app/{调用者文件名}_{调用者函数名}/_{步骤函数名}_{MMDD_HHMMSS}.png
```

文件名里的"调用者"由 `getCaller()` 从 `Error().stack` 里取第 4 帧（Python 版 `inspect.stack()[1]` 的等价物）。

## 五、最小可运行示例逐步拆解

```js
// test_case/suprecast_app/test_example.js
const path = require("path");
const { appTest } = require("../../common/app_common");
const { focusSearchInput } = require("../../app_sub_function/suprecast_app/android");

(async () => {
  const photosPath = path.join(__dirname, "..", "..", "report", "photo_app");
  const funcList = [
    [focusSearchInput, null],   // 步骤1：点搜索栏 → 进搜索页 → 聚焦输入框 → 输入 test → 回车
  ];
  await appTest(funcList, { photosPath });
  console.log("test_example.js 执行完成");
})().catch((e) => { console.error(e); process.exit(1); });
```

四要素，写新用例照抄这个骨架即可：

1. `require` 驱动 + 需要的业务函数；
2. `photosPath` 指向 `report/photo_app`；
3. `funcList` 数组，每项 `[函数引用, 参数字典或 null]`；
4. `appTest(...)` + 结尾 `.catch(... process.exit(1))`。

**注意 `funcList` 传的是函数引用，不是字符串**——`runAppSteps` 靠 `func.name` 打日志和命名截图，所以业务函数必须是**有名字的函数声明**，别用匿名箭头函数。

## 七、当前框架里已知的"待优化点"

这些是我读代码时发现的问题，正好可以作为我们后续一起动手的清单：

### P0 · 设备序列号硬编码，和实机对不上
- `app_common.js:20` `DEFAULT_DEVICE_SERIAL = "93e9db1c"`
- `app_common.js:206` **写死了常量**，而不是用 `appTest` 的 `options.deviceSerial` 参数 → 传参无效
- 实测本机设备是 `3B1F64EA9BBUTE00`，两者不一致，只是靠 `|| devices[0]` 兜底才没炸
- `android.js` 的 `getDevice()` 也直接取 `devices[0]`，同样忽略序列号

### P0 · `pkg` / `webviewTimeout` 参数定义了却没用
`appTest` 声明了这两个选项，函数体里从未使用（`getWxWebviewPage` 不接收 pkg；`withTimeout` 里的 5000ms 是硬编码）。

### P1 · 错误被截图逻辑覆盖
```js
} catch (e) { savedError = e; }          // 先存错误
  finally {
    if (photoPath) { await page.screenshot(...) }   // 若截图本身抛错且未被内层 try 抓住...
    if (savedError) throw savedError;    // ...原始错误就丢了
  }
```
内层 `try/catch` 只包住了 `mkdirSync` + `screenshot`，逻辑上还算安全，但 `stepTimes.push` 之后 `throw savedError` 会**直接跳出整个循环**，后续步骤不再执行——这与"希望跑完全部步骤再汇总"的测试诉求可能冲突。

### P1 · 没有断言层
目前唯一的"校验"是 `assertElementExists`（还是个操作函数），失败靠 Playwright 超时抛出。缺少：
- 文本断言、数值断言、页面跳转断言
- 明确的期望值/实际值输出
- 用例级的 `expect` 封装（让失败信息可读）

### P1 · 缺少 Python 侧统一入口
`common/__init__.py` 导入了 `sc_config` / `sc_log` / `sql_tools` / `test_common` / `test_decorator` / `web_decorator`，**这些文件当前都不存在**。
意味着：`import common` 现在会直接 ImportError；`base_config.py` 依赖的 `config/config.yaml` 也不存在。Python 侧能力（日志、配置、通知、数据校验）尚未接通 JS 链路。

### P2 · 用例层缺少组织能力
- 无 `pytest.mark.P0/P1` 的使用示例（pytest.ini 已注册 marker，但 JS 用例里没法打 marker）
- 无公共 setup/teardown：每个 JS 文件都要自己连设备、自己回到起点页 → 建议抽 `beforeEach` 风格的登录/进页公共步骤
- `pytest.ini` 里 `reruns = 1` 但注释写"全局失败重试2次"，注释与配置不一致
- `addopts` 里 `-p pytest_asyncio` 对纯 JS 用例无意义；`python_files = test_*.py` 与 JS 收集规则并存，未来混用时要注意

### P2 · 工程健壮性
- ~~无 `.gitignore`~~ ✅ 已补（含 SSH 密钥防护规则）
- ~~无 README~~ ✅ 已补（就是本文件所在的 docs/ 与根目录 README）
- ~~`android.js` 里选择器散落 / 硬编码~~ ✅ 已迁移到页面对象：
  `SEARCH_BAR` / `SEARCH_INPUT` 已随搜索逻辑移到 `pages/qa_page.js`；
  `switchToUserCenter` 的「我的」「积分商城」已移到 `pages/user_center_page.js`。
  `android.js` 现在只剩通用原子操作与断言
- `login()` 里的 `"4148"` 仍是硬编码测试数据，应外置到配置或参数化 —— **仍未做**

4. 切页后旧 page 会**降级为后台页**：它可能仍然活着、仍然在 `context.pages()` 里，但内容冻结，操作会等到超时。用 `resolveForegroundPage`（探测 `requestAnimationFrame` 是否还触发，并处理 page 已被销毁的情况）或 `findPageWith`（按选择器匹配）。`isVisible()`、`visibilityState`、`hasFocus()` 实测都无法区分前后台。注意过渡窗口中新旧页面会同时出帧，需要二次探测消歧。
5. 未聚焦时 `adb input text` 事件被系统丢弃，字输不进去但不报错 → 假通过。用 `dumpsys input_method` 的 `mInputShown=true` 确认。
6. `runAppSteps` 用 `func.name` 打日志、算耗时、命名截图文件；字符串无法调用，匿名函数没有有意义的 name。
7. `report/photo_app/{调用者文件}_{调用者函数}/_{步骤名}_{MMDD_HHMMSS}.png`；调用者信息由 `getCaller()` 从 `Error().stack` 反射取得。
