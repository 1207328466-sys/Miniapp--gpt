# knowledge — 长期事实知识

> 这里放"**当前是如何工作的**"这类**长期有效**的事实，供开工前先读。
> 与 `docs/踩坑记录.md` 的区别：踩坑记录是"踩过什么坑"的过程记录（含时间），
> 这里是结论本身。判断一段内容该放哪层，只问一句：
> **新会话开工前会读这个文件吗？** 会读 -> 放这里；只在回溯时看 -> 放踩坑记录。
>
> 本目录文件**必须登记在下表**，否则等于不存在（这条规矩借自团队工作流的「文档防腐规范」）。

## 知识来源

`工作项清单.md` / `迭代与模块汇总.md` 由超云生态平台（CodeArts）导出的工作项 xlsx 生成：

```powershell
# 把导出的 zip 解包到某个目录（每个 zip 里是一个 xlsx）
python tools/build_requirements_kb.py <导出解包目录>
```

**没有导出的部分**：需求正文/验收标准（GWT）在团队工作流仓的 `changes/<需求>/01-需求.md`，
不在本仓。要判断"某功能应该怎样"时，那里的 GWT + owner 才是口径 ——
代码注释、实现现状都不算（团队工作流里有专门一篇踩坑讲过这个）。

## 字段可用性（2026/10/10 用 30 列导出核实）

导出有两种格式，**只有 30 列那种带全字段**（13 列只有基础字段）。
用 30 列格式（101+101+48 行）实测各字段填充情况：

| 字段 | 情况 | 用途 |
|---|---|---|
| `描述` | ✅ 100/100 非空，平均 445 字、最长 2305 字 | **最有价值**：需求规格正文（规则/交互/字段限制） |
| `迭代` | ✅ 97/100 非空（Sprint1 ~ Sprint23） | 按迭代归类 |
| `故事点` | ✅ 98/100 非空 | 估规模 |
| `模块`、`领域`、`标签`、`发现环境` | ❌ **全空**（字段存在但没填） | 所以"按模块看"暂时做不到；功能域只能从标题归纳（见 `小程序功能地图.md`） |

> ⚠️ 想按**模块**统计的话，需要在平台上把工作项的"模块"字段填起来再导出——
> 这属于流程改进，不是导出方式问题。

## 描述里的内容长什么样（举例）

`小程序-发布帖子` 的描述直接写了硬性规则：每帖最多 9 张图且必传、标题 ≤100 字必填、
最多选 5 个话题、正文 ≤3000 字、机器审核（敏感词 + 图片识别）、
审核中/驳回的帖子只在个人中心可见、标题为空时发布按钮置灰。

**这类规则正是写用例时该断言的边界**（例如"标题为空时发布按钮不可点"就适合做一条断言）。
