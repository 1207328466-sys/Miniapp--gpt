# knowledge — 长期事实知识

> 这里放"**当前是如何工作的**"这类**长期有效**的事实，供开工前先读。
> 与 `docs/踩坑记录.md` 的区别：踩坑记录是"踩过什么坑"的过程记录（含时间），
> 这里是结论本身。判断一段内容该放哪层，只问一句：
> **新会话开工前会读这个文件吗？** 会读 -> 放这里；只在回溯时看 -> 放踩坑记录。
>
> 本目录文件**必须登记在下表**，否则等于不存在（这条规矩借自团队工作流的「文档防腐规范」）。

## 清单

| 文件 | 内容 | 什么时候看 |
|---|---|---|
| `小程序功能地图.md` | 被测小程序的功能域 → 页面 → 关联需求；以及"哪些是另一个产品、别混进来" | **写用例 / 判断某功能属于谁之前** |

| `迭代与模块汇总.md` | 按迭代/模块/领域/类型/状态的计数（**机器生成**） | 想快速知道"哪个模块改动最多" |

## 知识来源

`工作项清单.md` / `迭代与模块汇总.md` 由超云生态平台（CodeArts）导出的工作项 xlsx 生成：

```powershell
# 把导出的 zip 解包到某个目录（每个 zip 里是一个 xlsx）
python tools/build_requirements_kb.py <导出解包目录>
```

**没有导出的部分**：需求正文/验收标准（GWT）在团队工作流仓的 `changes/<需求>/01-需求.md`，
不在本仓。要判断"某功能应该怎样"时，那里的 GWT + owner 才是口径 ——
代码注释、实现现状都不算（团队工作流里有专门一篇踩坑讲过这个）。

## 已知的数据缺口（2026/10/10 导入时）

- 导出的格式**不统一**：大导出（13 列）只有基础字段；只有 30 列那种导出带 `模块`/`领域`/`迭代`/`发布版本号`。
- 因此 265 条工作项里，绝大多数 `模块`/`领域`/`迭代` 是空的（只有 11 条落在 Sprint22）。
  想要按迭代归类，需要按 30 列那种格式导出。
