# 环境与目标小程序

> **动手跑真机之前先读这一页。** 这里记的是"别把用例跑到错的地方/错的数据上"。

## 1. 两个环境是两个不同的小程序

| 环境 | 小程序 | appid | 说明 |
|---|---|---|---|
| **测试**（当前使用） | 超云生态平台（压铸人的社区百科） | `wx3de2e1d179b60303` | 框架当前测的就是它 |
| 生产 | 同名的另一个小程序 | **待补**（见下） | ⚠️ **同一部手机上可能同时缓存着它** |

> ❓**待 owner 补充**：生产小程序的 appid。
> 没有这个值，"别测到生产上"的安全阀就只能半开（见第 2 节）。

## 2. ⚠️ appid 安全阀（为什么需要它）

`resolveForegroundPage` 在拿不到 appid 时（例如开局落在 `/preload/` 空壳页）会
**按出现频次推断**该用哪个 appid。如果两个小程序同时被微信缓存，它**可能推断到生产那个** ——
之后所有断言都跑在生产小程序上，而且**不会报错**。

这与"设备序列号硬编码会静默连错设备"是同一类问题（后者已在第四轮修掉）。

**要求**：框架应支持显式声明"期望的 appid"，候选页里 appid 不符的直接排除，
一个都找不到就报错（宁可不跑，也不要跑到生产上）。

## 4. ⚠️ 数据安全：这台设备用的是真实账号

owner 已确认：**测试环境没有独立测试账号**，就用当前登录的这个账号。
所以"改数据"这件事必须显式开关，不能随手跑：

| 操作类型 | 例子 | 默认策略 |
|---|---|---|
| 只读 | 读页面、读进度、断言元素 | 正常执行 |
| **改前端状态** | 选答题选项、勾选筛选 | **需显式开关**（存在"选中即触发提交"的存疑） |
| **改服务端数据** | 提交答题、兑换积分、签到、下单、订阅、发帖 | **默认禁止**，需要 owner 明确同意 |

已落地的开关：`test_quiz_activity.js` 里的 `ALLOW_INTERACT` / `ALLOW_SUBMIT`（都默认 false）。

> 补充（2026/10/10 数据库实验结论）：答题活动的**「已答：N/M」是前端本地状态** ——
> 只点选项就会从 0/1 变 1/1，但**数据库一条记录都不写**（活动 347 的
> `home_activity_quiz_answer` / `_detail` 前后均为 0 条）。所以"点选项"安全，
> **真正写数据的是「提交」**。详见账本第二十一节。

### 4.3 答题页的交互规则（**口径来源：需求 713594985「小程序-答题赢积分活动」**）

> ⚠️ 这一节**以需求描述为准**（见 `knowledge/需求描述汇编.md` 的该条目），不是从界面反推的。
> 提醒自己：**做功能相关的事之前先读需求** —— 这次就是靠需求原文纠正了一个误判。

| 规则（需求原文口径） | 落地/实测 |
|---|---|
| 吸顶常驻「**已选**N/总数 · 答对最多可赢积分」 | 实现里显示成「已答： N /1」—— **语义是"已选"**，数的是选了几个，不是提交了几份。所以"选一下 0/1 就变 1/1"**符合设计** |
| **登录用户须答完全部题目才能提交**；提交前可修改 | 提交按钮在未选完时**禁用**（class 含 `activity-quiz-submit--disabled`）→ 可断言：初始 `禁用=true`，选中后 `禁用=false` |
| 提交后按钮变成「已提交已参加本次活动」状态，不可再次点击 | 我们实测未提交时按钮文本是「提交」——**这也反证了"没提交"** |
| **如未提交已选的选项不会保存** | ✅ 与数据库实验完全一致：只点选项后 `home_activity_quiz_answer` / `_detail` **前后都是 0 条**（账本第二十一节） |
| 再次进入：展示历史结果，不能再次作答 | 判据看 `home_activity_quiz_answer` 是否有记录 |
| 判分口径：单选/判断对则得分；**多选须所选集合与答案集合完全一致**；答错不扣分 | 适合做断言 |
| 每日总积分上限：仅「计入每日总上限」开关开启时生效；按自然日重置；截断时按剩余值发放并给专门文案 | 需要造数才能覆盖 |

**可直接变成断言的字段限制**（同一需求）：题目 1~15 题、题干 ≤200 字＋多图 ≤5 张、
选项 2~6 个且互不相同、每项 ≤50 字＋单图、判断题固定 A 正确/B 错误、
每题奖励积分为正整数、解析 ≤200 字符。

### 4.4 线上「答题」卡指向的活动会换人：同一条断言为何今天红、明天绿（2026/10/10 实测）

首页那张「答题」卡背后的活动**不是固定的**。实测到的先后两个：

| 时间 | 打开后看到的活动 | 形态 | 对断言的影响 |
|---|---|---|---|
| 10/10 上午 | `Z-B4-答题角标`（`home_activity` id 347） | **单题**判断题（A 正确 / B 错误） | 「选项恰好 2 个」「选项 2~6 个」都成立 |
| 10/10 下午 | `Z-题干图验证`（开发造的 15 题测试活动） | **15 题**题库；页面把全部题目的选项都渲染在 DOM 里（整页数到 52 个选项行） | 「选项数」类断言**不成立** —— 它只能数整页 |

因此：

- `pages/quiz_activity_page.js` 的 `assertQuizPageRules` 一旦识别出"多题活动 + 整页选项数超上限"，
  就按**不适用**上报（SKIPPED + 说明原因），不报失败；
- `test_case/suprecast_app/test_quiz_activity.js` 开头加了一步前置条件检查，多题活动直接记跳过。

> 教训：**页面对象里带具体数字的断言，天然依赖数据形态。**
> 写这类断言时要顺手问一句"数据换一种形态时它还成立吗"，
> 并为不成立的情况准备一个明确的说法（跳过 + 原因），别让它变成一条没人看的红。

### 4.5 首页筛选 tab 的"选中态"判据（2026/10/10 真机实测）

首页信息流那排筛选 tab（最新提问 / 推荐 / 精选问答 / 我的关注）**没有 class 表达选中态**，
只能读计算样式。实测（探针 `test_case/diagnostic/probe_feed_tabs.js`，切换前后两次快照对照）：

| | 选中 | 未选中 |
|---|---|---|
| color | `rgba(0,0,0,0.88)` | `rgba(0,0,0,0.48)` |
| font-weight | 500 | 400 |

- 判据实现在 `app_sub_function/suprecast_app/pages/qa_page.js`（`readFeedTabs` / `activeFeedTab`），
  阈值 0.8 / 500；判据失效时错误信息里会带出四个 tab 的原始值，方便重新校准。
- ⚠️ 小程序**会记住上次选中的 tab**（不会自动回到「最新提问」），所以
  「回到首页」收尾会归位到「最新提问」，「检查活动入口」跑完也会自己还回来（坑 18）。
- ⚠️ 学习中心那排顶部 tab 用的是 `class active`（另一套组件）—— **别把两处判据互相套用**。
- ⚠️ 和某个 tab 同名的元素在整页里不止一处（卡片角标也写着「推荐」），
  所以读状态必须先锁定"同时含 4 个 tab 文案的最内层容器"（= tab 栏）。

## 5. 同一部手机可能被别的 AI / 别人同时操作

团队工作流里把这条单列一节，因为它**让错误的结论被真实的证据支撑**：
你观测到的现象是真的（画面确实变了），但原因归错了（以为是框架缺陷），
于是会去"修"本来正确的代码。

**实践纪律**：

1. 动手前先截图确认现场，不要假设"我上次离开时它在哪"
2. **偶发失败先怀疑环境，再怀疑代码**
3. 长流程前先确认独占
4. 一个具体教训：实测出现过"步骤 1 时还在答题页，8 秒后页面已经回到首页"，
   断言报"选项命中 0 个"——**断言是对的，是页面被切走了**
