# 缺陷回归清单（从 545 条缺陷里筛出来的"值得盯住的"）

> 这份清单回答一个问题：**哪些已经修过的历史缺陷，值得用真机 UI 用例盯着，不让它复发？**
> 数据来自 CodeArts（原始数据 `report/需求拉取/详情缓存.json`，人读版 `缺陷描述汇编.md`）。
> 粗筛规则可复现：`python tools/screen_bug_candidates.py`（545 条 → 327 条候选），
> 之后**由人**从候选里挑 —— 脚本不猜断言，断言必须来自缺陷原文 + 真机实测。

## 一、结论先放前面

1. 545 条缺陷里，粗筛剩 327 条；人工复筛后**只有 4 条**同时满足
   「简单 + 只读 + 不依赖脏数据 + 能用现有 53 个动作表达」，已经写成表格用例，
   2026/10/14 在真机上跑通（`ZW_001`~`ZW_004`）。
2. 剩下的**绝大多数不该硬做成 UI 用例**。它们分成六类（见第四节），
   硬做的结果只有两种：永远红（假失败）或者永远绿（假绿）—— 两种都比"没这条用例"更坏。
3. 一句话口径：**缺陷回归用例要"少而准"**。界面上守得住的守住；
   接口返回、后台列表、积分计算那几类，归接口/后台自动化管，别塞进真机 UI 里。

## 四、这份筛选怎么复现

```powershell
python tools/screen_bug_candidates.py                 # 只看看有多少候选、抽前 10 条
python tools/screen_bug_candidates.py --out <文件>     # 落一份完整清单（md 表格）
python tools/screen_bug_candidates.py --selftest       # 只跑规则的正反例（离线）
```

- **只挑状态是「已关闭 / 已解决」的**：还没修好的缺陷，写成用例只能永远"跳过"；
- 粗筛是**宁滥勿缺**的：它只看标题关键词，会有已知误差（例如"未返回"里的「返回」
  被当成界面词，把一条接口缺陷也捞进来）—— 所以后面必须有人复筛，脚本不替你下结论；
- 需求那边的同类清单是 `可自动化需求清单.md`（那份管"新功能"，这份管"老毛病"）。

## 五、写缺陷回归用例的四条纪律（都是从这轮实做里来的）

1. **断言看缺陷原文，不看现状**：原文说"应该是 X"，就断言 X；拿当前界面当口径，
   等于把 bug 固化进用例（本项目铁律：不凭猜测写断言）。
2. **优先只读**：一上来就写会改数据的回归用例，很快就会变成"没人敢跑"的用例集。
3. **核心断言必须反向验证**：先证明"缺陷在的时候这条会红"。`ZW_003` 差点写成假绿 ——
   最初想断言「评论面板出现『发送』」，实测发现**点的前后 DOM 里都有那个节点**
   （面板预先渲染好、隐藏着），所以断言改成了"和「检查文字显示」同一个口径"的
   可见文字判断，并当场正反两验（详见 `docs/踩坑记录.md` 坑 35）。
4. **前提必须是可预期的**：依赖"线上某条帖子/某个案例"的用例，明天就可能假红 ——
   这也是第三节 B 那些缺陷迟迟没写成用例的原因。
