# 前端源码 ↔ 我们的选择器对照（**小程序前端源码在哪、每个选择器从哪来**）

> 前端源码（owner 2026/10/15 给的，**另一个仓**）：`C:\Users\admin\Desktop\eco-microapp`（Taro + React）。
> 这份文档回答一件事：**框架里那些选择器/判据是从哪儿来的、源码哪一行能佐证**。
> 以前只能"打印页面结构抄 class"（改版就得重抄一遍）；有了源码，抄完之后能**回头核对**，

## 五、怎么用这份对照（写用例/改页面对象时的习惯）

1. **先看源码确认"这个元素是不是稳定的"**：源码里写死的 className ✅；`text-_h3D3D3D_` 这种
   "颜色被编译成类名"的 ⚠️ 只当辅助，别当主判据；
2. **判据优先用"源码里表达的语义"**：tab 选中看 `active` 类、活动类型看 `ACTIVITY_TAG` 的映射、
   "进了哪一页"看**页面根容器**（`.qa-page` / `.cases-page` / `.case-detail-page` / `.activity-quiz-page`）；
3. **判据冲突以真机为准**，但把源码里那句话抄进注释（例如"答题本期不跳转"），下次就不用再猜一遍；
4. 源码不覆盖的（例如"哪一页在屏幕上"）仍然靠实测建立判据（见坑 46：输入归属）。

## 六、找不到锚点时：`tools/scan_anchors.py`（2026/10/16 加）

上面那几张表是**已经用上的**锚点；要写**新**用例、想找一个"源码里叫什么"的类名时，用这个工具查：

```
python tools/scan_anchors.py --find case          # 按关键词找类名（前面加个点就能填进表格）
python tools/scan_anchors.py --find tab --in qa   # 限定在某个页面/组件里找
python tools/scan_anchors.py --module cases       # 看这个页面/组件下都有哪些类名
python tools/scan_anchors.py --check-doc          # 校验本文档里教的锚点，源码里都真的存在
```

它扫的是 `eco-microapp/src` 下所有 TSX 里的 `className`（三种写法都吃：`className="a b"`、
`className: "a b"`（props 对象里的）、`className={rootClassName}`（名字存在变量里的 ——
`eco-tabs-bar` 就是这么写的，第一版工具漏了它，当场报了个假警报）。

**它只做"查"和"核对"，不生成大清单**：源码里有 1700 多个类名，其中绝大多数是**原子类**
（`fs-28`、`text-_h3D3D3D_`、`whitespace-nowrap`…），全列出来只会淹掉真正有用的那几十个。

## 七、这次用源码换来的三处改进（2026/10/16）

### 7.1 原子类 vs 业务类名：抄错的那一类，框架现在会当场提醒

真机 DOM 里两者**长得一样**，分不出来；源码里一眼就能分：

| | 长什么样 | 例子 | 能不能当锚点 |
|---|---|---|---|
| 业务类名 | 写页面时自己起的（源码 TSX 里手写） | `eco-tab-item`、`case-list-card`、`overlay-mask` | ✅ 稳（实测运行时 DOM 里原样保留、无 hash 后缀） |
| 原子类 | 样式系统编译出来的样式名 | `fs-28`、`text-_h3D3D3D_`、`whitespace-nowrap` | ❌ 一屏到处都是、改版就烂 |

所以框架里现在有一道判据（`base_page.js` 的 `looksLikeAtomicClass`）：
填表时写了原子类，**操作照做**，但日志与报错里会提醒一句，并指路 `--find`。
（只提醒、不拦截：万一哪天真的只有原子类可用，也不该把用例卡死。）

### 7.2 文字重名：用「范围内点文字」圈范围

实测（2026/10/16，首页）：`推荐` 这俩字**整页命中 2 处** —— 一处是筛选 tab，
另一处是信息流里某张卡片的标题。`点文字` 只按 DOM 顺序取第 N 个，**点对了是运气**。

圈定范围之后就只剩一处：

| 想点的东西 | 整页按文字找 | 圈进范围找 | 范围 |
|---|---|---|---|
| 筛选 tab「推荐」 | 2 处（还有一张卡片标题也叫「推荐」） | **1 处** | `.eco-tab-bar-container` |
| 底部 tab「我的」 | 2 处（还有一个是筛选栏的「我的关注」） | **1 处** | `.custom-tab-bar` |

表格里的写法：动作 **「范围内点文字」** —— 参数1 填范围（`.eco-tab-bar-container`）、参数2 填文字（`推荐`）。
页面对象里已经按这个口径改过：`switchToFeedTab` / 切底部 tab 都先圈范围（`base_page.tapBottomTab`），
范围不在时才退回老写法**并打一行日志说明退回了**。

**为什么不写成 `.eco-tab-bar-container span:has-text("推荐")`**：`:has-text()` 会把**祖先全算命中**
（容器、内容区、文字节点都在内），再按"第几个"挑，挑到哪一层全看 DOM 顺序 —— 那是"看着有选择器、
其实还在猜"。`getByText` 的实测口径是**只给最内层那个放文字的节点**
（`最新提问` 整页命中 1 个 = 那个 `span`；`推荐` 的 2 处也都是 `span`）。

顺便一个副产品：命中多处时，框架会把**候选一个个打出来**（标签、class、坐标、前 20 字），
并标出实际点了哪一个 —— "点错地方"在报告里从此看得见。

### 7.3 点击前等它停（`android.js` 的 `tapElement`）

"量坐标"和"adb 真的点下去"之间隔着一小段时间。这段时间里元素要是还在动，
点到的就是它**刚才待过**的位置 —— 页面没反应，而且不报错（跟坑 20 / 坑 25 同一族）。

页面为什么会动，源码里写得明明白白（不是猜的）：`components/eco-tabs-bar/index.tsx` 里，
点完 tab 会 `scrollTo({ left, duration: 200 })` —— **一次点击之后那条栏自己要滚 200ms**；
页面切换（Taro navigateTo）本身也是动画，切的过程中两页坐标都在动。

做法：点之前再量一次坐标 —— 两次一样就直接点（页面没动时只多花几毫秒）；
不一样就等 180ms 再量，最多 4 轮；4 轮还没停就用最后一次的坐标点，并把"它一直在动"打出来。
