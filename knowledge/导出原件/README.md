# 导出原件（超云生态平台 / CodeArts 工作项导出）

> 这里放**平台导出的原始 xlsx**，作为 `knowledge/` 下三份生成物的唯一来源。
> **不要手改这些文件**（改了就对不上生成物）。文件名是平台自动生成的，含导出时间戳。

## 为什么两种格式都要留

| 格式 | 内容 | 为什么留 |
|---|---|---|
| **30 列**（101/101/48 行） | 带 `模块`/`领域`/`迭代`/`发布版本号`/`故事点`/**`描述`** | `描述` 是需求正文（平均 445 字）——写用例的边界值主要来源 |
| **13 列**（101/101/48 行） | 只有基础字段 | 与 30 列是同一批数据，**冗余**（保留是为了对照，不产生新条目） |
| **小导出**（6~12 KB，Bug 列表） | Bug 专用格式 | ⚠️ **30 列那批里没有这些 Bug** —— 实测 18 条缺陷（含「首页活动跳转压铸百科，底部导航栏消失」这类正对自动化的）只存在于这些小导出里 |

**一句话**：只留 30 列会导致"仓库里的原件生成不出现在的知识库"（265 条会掉到 247 条），
所以三类都留。判断标准很简单：**只用本目录能否重建出与已提交一致的知识库**。

## 新增迭代的入库流程

1. 平台导出工作项（优先选 **30 列**那种；Bug 列表单独导）
2. 把 zip 解到本目录（保持平台生成的文件名）
3. 重新生成三份知识文档：

   ```powershell
   python tools/build_requirements_kb.py knowledge\导出原件
   ```

4. 确认条目数变化合理（新增迭代应只增不减），然后提交

## 字段可用性（2026/10/10 实测）

| 字段 | 情况 |
|---|---|
| `描述` | ✅ 100/100 非空（平均 445 字，最长 2305 字） |
| `迭代` | ✅ 97/100 非空（Sprint1 ~ Sprint23） |
| `故事点` | ✅ 98/100 非空 |
| `模块`、`领域`、`标签`、`发现环境` | ❌ **全空**（字段存在但平台上没填）→ "按模块统计"暂时做不到 |
