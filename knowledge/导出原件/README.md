# 导出原件（超云生态平台 / CodeArts 工作项导出）

> 这里放**平台导出的原始 xlsx**，是 `knowledge/` 下三份生成物的唯一来源。
> **不要手改这些文件**。文件名由平台生成，带导出时间戳。
>
> **本目录只放「需求（Story）」的导出** —— 这是 owner 定的口径（见下方"关于 Bug 列表"）。

## 保留的是哪种导出

| 格式 | 内容 | 是否保留 |
|---|---|---|
| **30 列完整版** | 带 `模块`/`领域`/`迭代`/`发布版本号`/`故事点`/**`描述`** | ✅ **保留** —— `描述` 是需求正文（平均 445 字），写用例的边界值主要来源 |
| 13 列精简版 | 只有基础字段 | ❌ 已移除：与 30 列是同一批数据，**不产生任何新条目** |
| Bug 列表小导出（6~12 KB） | Bug 专用格式 | ❌ 已移除：**导出错了**（owner 2026/10/10 确认），本知识库只记需求 |

校验标准很简单：**只用本目录能否重建出与已提交一致的知识库**。
（当前：4 个 30 列导出 → 247 条需求，与已提交的 `工作项清单.md` 一致。）

## 关于 Bug 列表（别再加回来）

过程中曾把 Bug 列表小导出也解进本目录，一度让条目数从 247 涨到 265。
owner 确认那份 **Bug 导出是导错了**，而且本知识库的定位是"记住需求、理解小程序功能"，
所以已把那 8 个非需求导出移除。

**如果以后需要缺陷做回归靶子**：请单独导出、单独存放，**不要混进本目录**
（否则生成物里会混入非需求条目，口径就不清了）。

## 新增迭代的入库流程

1. 平台导出工作项，**选 30 列那种**（只导需求 / Story）
2. 把 zip 解到本目录（保持平台生成的文件名）
3. 重新生成三份知识文档：

   ```powershell
   python tools/build_requirements_kb.py knowledge\导出原件
   ```

4. 确认条目数**只增不减**（新增迭代应该是增量），再提交
